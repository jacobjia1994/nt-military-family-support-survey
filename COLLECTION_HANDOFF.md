# Collection, migration and analysis handoff

Updated 29 September 2026. This is a proposal for Lutheran Care (LC) and its IT team. The GitHub Pages questionnaire is a **public preview without a response receiver**. No platform, tenant, receiving endpoint, access group or retention period is selected by this document; no real response was collected by preparing it.

## Instrument and source

The adult and 8–17 questionnaire uses schema 9.0, revision 2026-09-29-rand-linked-needs. Its main route adapts the linked problem → need → contacted or uncontacted resource → barrier/bridge → met-need approach in [Miller et al., RAND 2011, Appendix A](https://www.rand.org/pubs/monographs/MG1124.html). The source survey was for US adult service members/spouses. Local item wording, nine adult groups/45 cues and the short youth route are adaptations, not RAND-validated NT instruments. The under-7 guardian-supported schema 1.3 remains separate, with wording revision 2026-09-29-local-connection-preview and in-memory preview storage only.

The platform-neutral question bank is generated by scripts/export-handoff.mjs from the live definitions. Use it with [FLOW_REDESIGN.md](FLOW_REDESIGN.md) and the source commit; it is not an automatically configured Microsoft Form or receiving service. A source archive is a portable front end only. The current preview notice and finish screen correctly state that answers are neither sent nor saved; do not change that claim until a real receiver confirms a stored record.

## Functional contract for production

A candidate platform must demonstrate the following with invented test answers:

1. External participation and the correct adult, 8–17 and under-7 permission routes.
2. An adult problem screen with grouped concrete cues, Other write-in and an explicit no-listed-problem route where the live form provides one; a shorter youth route; no silent loss of selected cue codes.
3. Selection of up to two categories for structured depth while retaining all other reported problems. Chosen categories display only their applicable follow-up questions; a change to an earlier answer does not leave stale hidden values in the export or reassign a prior chain to another need.
4. For each chosen **adult** category, optional focus_problems selected from that category's checked concrete cues, all reported help types (including explicit no help needed), and up to two help types for deeper follow-up. Up to four adult category × need pages then distinguish seeking, receiving, source contact, applicable barrier/bridge, overall met status and current gap. The youth version uses a shorter category-level sequence. Selected problem, needed assistance, contacted support, received help and met outcome must remain separate values.
5. Optional positive support, future need and further accounts. For the 100-account supplemental capability, test 0, 1, 10 and 100 active entries, a rejected 101st, removal/replacement, stable IDs, back/forward editing and full export. Do not reduce this ceiling silently to two or ten.
6. Optional broad residential area and matching optional suburb/locality; a separate current Greater Darwin work/posting connection; historical/outside/undisclosed routes; review/edit; and a true submission acknowledgement only after durable storage. Do not map an outside-area worker or posted member to a local-resident count.
7. A separate interview-request receiver with safe-contact permissions and no survey/contact join key. The free support guide remains accessible without survey participation.

The adult web front end allows 5,000 characters in a long answer and youth 1,500. A migration must preserve intended text capacity or show an agreed, usable continuation design; never silently truncate. Microsoft Forms branching, question limits and exact export behavior need a **tenant prototype**, not an assumption. [Microsoft Forms branching](https://support.microsoft.com/en-gb/forms/use-branching-logic-in-microsoft-forms), [form limits](https://support.microsoft.com/en-us/forms/form-question-response-and-character-limits-in-microsoft-forms).

## Two implementation routes

| Decision point | LC Microsoft 365 Forms | Current front end with LC receiver |
| --- | --- | --- |
| Public entry | Link or embed LC-owned Forms, subject to tenant rules for external respondents. | Host static questionnaire and use an LC-approved HTTPS API. |
| Complex branches and repeats | Prove the full category route and optional repeat behavior in a real tenant prototype. | Reuse the tested browser flow and implement matching server validation. |
| Records | LC Forms response service and supported restricted workbook/export. | LC-approved database or records system and documented export. |
| Ownership | Restricted LC group, at least two continuity owners and approved analyst access. | Named frontend/API/data owners and restricted administration. |
| Response notice | State the actual Forms/SharePoint custody and LC process. | State the actual API/data-store custody and LC process. |

Embedding a form does not move its response storage to LC's website. Current Forms data location cannot be inferred from LC being Australian; IT should verify the tenant's actual location, backup and retention arrangements. [Microsoft Forms data storage](https://support.microsoft.com/en-us/forms/data-storage-for-microsoft-forms). A Forms workbook should remain in its supported SharePoint connection; analysis work should use a separate extract. [Forms results/export](https://support.microsoft.com/en-us/forms/check-and-share-your-form-results).

If LC uses the custom front end, the receiver must accept a **versioned allowed-field schema**, separate survey/contact endpoints, HTTPS and LC's normal access, backup and monitoring. It must durably store a record before acknowledging success, retain entered answers in the browser on failure, and support retry with a submission-scoped idempotency key. Never place server credentials in browser code or actual responses in this public Git repository. Test receipt, export, failure/retry, duplicate clicks and role-based access with invented responses. Do not use email, downloaded files or concurrent Excel appends as the primary response store.

## Source and analysis records

Preserve the original submitted payload and source ID, instrument/age route, schema and questionnaire revision, submission time, collection stage, recall context, consultation route, broad area/locality precision, and exact option codes. Freeze wording, options and branches alongside every release. A field meaning or recall-period change needs a new revision and an explicit comparison rule.

Suggested export grains:

| Table | One row represents |
| --- | --- |
| responses | One submitted record; identity is not assumed unique. |
| problem_cues | One selected concrete problem code in a response, with category and display order. |
| detailed_categories | One category chosen for linked follow-up in a response. |
| help_selections | One selected help type or optional focus type within a detailed category. |
| need_chains | One chosen category × prioritised help type followed in detail. |
| contacts | One approached or used source, or explicit no-contact answer, within a need chain. |
| source_outcomes | One optional per-source answer about receipt and contribution to that specific linked need. |
| outcomes | Seeking/receipt state, explicit overall met-status across sources, applicable barrier/bridge and current gap for one need chain. |
| accounts | One optional supplemental account, retaining stable ID, order, verbatim text and applicable context. |
| dictionary | The exact question/option/branch definition for one revision. |

A selected problem cue is **not** an unmet need. Unselected cues and blank optional answers are not explicit No. An unchosen detail category does not imply the issue was unimportant or resolved. No contact does not prove a barrier; contact does not prove helpfulness. Preserve positive_support and future_need separately from the past-problem chain. Keep child expressions and guardian observations distinct. The survey dataset must not contain interview contact details or a hidden join ID.

Analyse response counts and each later unit at their proper denominator. Volunteer responses cannot estimate prevalence among all Defence families in Greater Darwin. Keep schema 9.0 separate from schemas 8.1, 8.0 and 7.2 unless a documented item-level comparison supports a particular measure. See [ANALYSIS_PROTOCOL.md](ANALYSIS_PROTOCOL.md).

## LC decisions before collecting real answers

LC and IT need to name the receiving platform and owners, prove external access and all branches/repeats with invented data, establish actual data location/access/retention, set the live participant notice, verify an end-to-end submission plus export, and appoint someone to check the separate interview-request channel using its safe-contact rules. A preview link or a passed browser test does not complete collection setup.
